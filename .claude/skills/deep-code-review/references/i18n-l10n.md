# Internationalization & localization — depth (domain R)

**Read this when** the target renders user-facing text in more than one language
or locale, accepts user-supplied Unicode text, or the review question is "is this
correct across locales and scripts?" It is the depth behind domain R's
at-a-glance checklist in `domain-checklists.md` (§R) — the standards-heavy
correctness a checklist can't hold. Cross-link the checklist; don't restate it.

## Encoding & Unicode normalization
- **UTF-8 everywhere, declared in-document.** W3C i18n: "Choose UTF-8 for all
  content," and "always use an in-document encoding declaration, even if you are
  also using the HTTP header." When a document's bytes and its declared encoding
  disagree, non-ASCII text mojibakes silently.
- **Normalize before you compare, dedup, or key on user text — and normalize
  *after* concatenation, not before.** Two visually identical strings can be
  different byte sequences (`é` as one code point vs `e` + a combining accent), so
  an equality check, a `GROUP BY`, a uniqueness constraint, or a cache key over
  un-normalized user text treats equal strings as different. Normalize to one form
  (NFC is the web default — W3C recommends it). The subtle trap: **"None of the
  Normalization Forms are closed under string concatenation … even if two strings
  X and Y are normalized, their string concatenation X+Y is _not_ guaranteed to be
  normalized"** (Unicode UAX #15). A pipeline that normalizes fragments and then
  concatenates can still emit un-normalized output — normalize at the boundary
  where the value is compared or stored, *after* assembly. (The checklist's
  🚩 "concatenated translated fragments" is this defect's surface form.)

## Bidirectional text (RTL) and the bidi-override attack
- **Declare direction; don't rely on the renderer guessing.** W3C i18n: add
  `dir="rtl"` when the overall document direction is right-to-left, and "tightly
  wrap every opposite-direction phrase in markup that sets its base direction." An
  RTL string (Arabic, Hebrew) interleaved with LTR runs (numbers, Latin
  identifiers) reorders incorrectly without an explicit base direction — a
  displayed IBAN, price, or file path can render in the wrong visual order.
- **Reject or flag Unicode bidi control characters in source and in untrusted
  input.** UAX #9 (the Unicode Bidirectional Algorithm) defines explicit
  directional-formatting controls in distinct classes: **overrides** (RLO/LRO),
  embeddings, **isolates** (RLI/LRI/FSI/PDI — the *safer* mechanism the
  direction-wrapping bullet above relies on), and the terminators PDF/PDI. UAX #9
  says the **overrides** in particular "are to be avoided wherever possible, because
  of security concerns" (see Unicode UTR #36). This is the Trojan-Source class: a
  bidi control in a source comment or string literal can make code *read* in review
  as the opposite of what compiles (the attack abused isolates as well as
  overrides), and in user content can spoof a displayed value — so flag bidi
  controls broadly in source and untrusted input, not only the overrides.
  (`domain-checklists.md`
  flags zero-width / bidi control characters for instruction-smuggling in code —
  the invisible-character check; this is the rendering-and-review-legibility side
  of the same characters.)

## Plurals, formatting, and collation
- **Plural selection uses the locale's CLDR categories, never `n == 1`.** Unicode
  CLDR defines up to six plural categories — **zero, one, two, few, many, other** —
  and "languages vary in how they handle plurals"; a hardcoded
  `count === 1 ? singular : plural` is wrong for languages with dual/paucal forms.
  **`other` is the required default** every language has. Route plurals through an
  ICU / CLDR-backed API, never string concatenation of a count with a fixed suffix.
- **Format numbers, dates, currency, and times through a locale-aware formatter.**
  Grouping separators, decimal marks, calendar system, first-day-of-week, and
  12/24-hour clock all vary by locale; a hand-rolled format is correct only for the
  author's locale. And **sort / collate with a locale collator, not a byte or
  `.sort()` compare** — `.sort()` on localized text orders by code point, which
  mis-orders accented and non-Latin scripts (the checklist's 🚩 ".sort() on
  localized text"). A collation test asserts the *locale's* expected order, not the
  ASCII order.
- **Leave room for text expansion.** Translated strings run longer than English
  (German and Finnish are the usual worst cases); a layout that fits English
  exactly clips or overflows once localized. Verify the running UI in a
  long-string locale, not only in English (cross-ref `product-ux-quality.md` layout
  invariants across the sweep matrix).
