Do **not** close and reopen your pull request. Doing so will delete the existing review thread, lose Jane's comments, and force her to start her review from scratch, which is frustrating for maintainers. You can safely rebase and update your existing PR while preserving the conversation.

Follow this procedure to align your fork with upstream `main` without losing review context:

1.  **Fetch the latest upstream state:**
    Ensure your local git knows about the current `main` branch on the upstream repository (not just your fork).
    ```bash
    git fetch origin
    ```
    *(Note: Replace `origin` with the remote name for the upstream LogFlow repo if you use a different name like `upstream`.)*

2.  **Rebase your feature branch:**
    Switch to your feature branch and rebase it onto the fetched `main`.
    ```bash
    git switch <your-branch-name>
    git rebase origin/main
    ```
    If there are conflicts, Git will pause. Resolve the conflicts in your files, then run:
    ```bash
    git add <resolved-files>
    git rebase --continue
    ```
    Repeat until the rebase finishes. This rewrites your local commit history to sit on top of the latest `main`, creating a linear history as requested.

3.  **Force-push with lease protection:**
    Since rebasing rewrites commit hashes, you must force-push to your fork. However, use `--force-with-lease` instead of plain `--force`. This safety check ensures you don't accidentally overwrite changes if something else pushed to your fork in the meantime.
    ```bash
    git push fork <your-branch-name> --force-with-lease
    ```
    *(Note: Replace `fork` with the remote name of your personal fork.)*

**Why this preserves the review:**
GitHub links review comments to the **file path and line content**, not strictly to the commit hash. When you push the rebased branch, GitHub automatically migrates Jane's comments to the new commits as long as the surrounding code context remains recognizable. The PR URL stays the same, and the conversation thread remains intact.
