Since I cannot share the specific proprietary implementation details of these external systems due to confidentiality agreements, I hope you can accept this high-level impact assessment: changing the signature now will break valid, existing use cases that are out of our immediate control.

To balance your valid architectural concerns with the need to maintain stability for current users, I propose the following compromise:

1.  **Preserve the Current Signature:** We keep the existing parameter order as the primary public API for this release cycle to ensure continuity for downstream users.
2.  **Introduce a Deprecation Path:** We can add a clear deprecation warning in the documentation (and via runtime warnings if feasible) indicating that the parameter order is scheduled to change in the next major version (e.g., v2.0). This gives external teams the official notice they need to begin their internal update processes.
3.  **Internal Refactoring:** If the internal logic simplification is significant, could we achieve this via an internal adapter pattern? We could accept the current public signature and immediately map it to your preferred internal argument order within the function body. This gives you the clean internal logic without breaking the public contract.

I understand the project's hesitation regarding accumulating legacy code or deprecation debt. However, introducing a time-bound deprecation window seems preferable to an immediate breaking change that disenfranchises current users. This approach respects the project's evolution while honoring the implicit contract with existing integrations.

Does this middle ground work for you? If the project strictly forbids deprecation aliases, please let me know, and I can open a separate issue to discuss the timeline for a coordinated breaking change in a future major release, allowing affected parties time to prepare.
